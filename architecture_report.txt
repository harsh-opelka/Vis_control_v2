1. DETECTION RESULT STORAGE
================================================================

The raw per-frame Hough result is returned as a `ClothTrackingResult`
(defined in viscontrol/detection/pipeline.py:71-87) by
`InspectionPipeline.run_cloth_tracking()` (viscontrol/detection/pipeline.py:277).
It is a plain dataclass with fields including `detections`,
`front_row_centroids`, `tripwire_occupied`, `tripwire_occupancy`,
`row_profile`, `row_profile_scale`.

This result is NOT stored on `InspectionPipeline` or `ClassicalDetector`
itself — those are stateless per call. It is stored on `MainWindow`
(viscontrol/ui/main_window.py), which owns three cache fields:

    self._cached_cloth_detections      (main_window.py:205)
    self._cached_cloth_highlight       (main_window.py:206)
    self._cached_tripwire_occupied     (main_window.py:207)

These are populated only when Hough actually runs this frame
(main_window.py:748-763):

    if _hough_due:
        ...
        r = self._pipeline.run_cloth_tracking(
            frame, profile, self._cfg.detection,
            bg_reference_cloth=self._bg_reference_cloth,
        )
        ...
        self._cached_cloth_detections = r.detections
        self._cached_cloth_highlight = list(r.front_row_centroids)
        self._cached_tripwire_occupied = r.tripwire_occupied
        cloth_detections = r.detections
        highlight = r.front_row_centroids
        _tripwire_occupied = r.tripwire_occupied

YES — this cache IS reused across multiple frames without re-running Hough.
Hough is rate-limited to `hough_interval_ms` (config/default.yaml:126,
default 100ms) and further gated by `tripwire_check_interval`
(config/default.yaml:43). On frames where Hough is NOT due
(main_window.py:825-829):

    else:
        # Hough not due this frame — reuse cached cloth results for display.
        cloth_detections = self._cached_cloth_detections
        highlight = self._cached_cloth_highlight
        _tripwire_occupied = self._cached_tripwire_occupied

The cache is also used as a fallback for the DISPLAY path even when the
cloth is stopped (main_window.py:1011-1018), so the overlay stays visible on
a static scene without detection re-running.

Reset points: the cache is cleared to empty on `_disable_detection()`
(main_window.py:601-603) and effectively re-seeded on the next
TuchabzugRunning rising edge (`_last_hough_time = 0.0` forces an immediate
Hough run — see `_reset_tracking_session`, called at main_window.py:733).

Other, unrelated per-frame storage on MainWindow (not Hough-result caches,
listed for completeness):
    self._latest_frame       (main_window.py:129, 650) — the raw camera
        frame, used later for on-demand re-processing (snapshot capture,
        reference capture), not a detection-result cache.
    self._latest_annotated   (main_window.py:130) — declared but never
        written to or read elsewhere in the file; effectively dead.

Separately, `ClusterTracker.tracked` (viscontrol/detection/proximity_clustering.py:120-134)
and `DonePieceTracker` persist cross-frame *cluster identity* state (which
physical row/cluster is PENDING vs DONE), but this is derived fresh from
`cluster_by_tangent()` output every frame it runs — it is not a cache of
raw Hough circles, it is a cache of decided cluster identities.

2. DRAW / DISPLAY CADENCE
================================================================

Drawing is a SEPARATE step from detection, not the same function.

Detection happens inside `MainWindow._on_frame()` (main_window.py:627),
gated by `_hough_due` (main_window.py:740-745) — runs at up to
`hough_interval_ms` (100ms / ~10Hz) subject to `tripwire_check_interval`.

Drawing/UI-update is gated separately, later in the same `_on_frame()`
method, by a fixed ~15fps display cap (main_window.py:74-77, 929):

    _DISPLAY_INTERVAL_S: float = 1.0 / 15.0   # ~15 fps display cap
    ...
    if _now_mono - self._last_display_refresh >= _DISPLAY_INTERVAL_S:
        self._last_display_refresh = _now_mono
        ...
        self._inference_view.set_cloth_frame(
            cloth,
            detections=cloth_detections,
            ...
        )

The draw block reads whatever `cloth_detections` holds at that point in
`_on_frame` for THIS call — which, per section 1, is either a fresh Hough
result (if Hough ran this frame) or the cached
`self._cached_cloth_detections` (if not, or if empty and cache is
non-empty — main_window.py:1015-1018). So the draw function reads a
per-frame local variable that is itself backed by the cache, not the cache
object directly, and not guaranteed fresh.

Call chain for the actual pixel-level drawing:
    1. MainWindow._on_frame (main_window.py:627)
       -> InferenceView.set_cloth_frame() (viscontrol/ui/views/inference_view.py:418)
    2. InferenceView.set_cloth_frame
       -> CameraView.set_state() (viscontrol/ui/widgets/camera_view.py:639)
    3. CameraView.set_state
       -> _Canvas.set_state() (camera_view.py:115-117) — stores the
          `CameraViewState` dataclass snapshot and calls `self.update()`
          (a Qt repaint request; does not paint immediately).
    4. Qt later calls _Canvas.paintEvent() (camera_view.py:119) on the GUI
       thread, which reads `self._state` (the stored snapshot, NOT a fresh
       detection run) and paints the image + all overlays, via
       `_draw_detection` (camera_view.py:317), `_draw_highlight` (447),
       `_draw_proximity_clusters` (505), `_draw_transfer_events` (542), etc.

So: paintEvent is a pure re-render of the last snapshot handed to it by
`_on_frame` — it never triggers or reads live detection. It can also fire
independently of `_on_frame` (e.g. on window resize/expose), in which case
it simply repaints the same stale `self._state` again.

================================================================

File: viscontrol/ui/main_window.py
Function: `_apply_cluster_stop_edge()` (main_window.py:1389), described in
its own docstring as "the sole StopTuchabzug fire-decision owner".

It is called only when Hough actually ran this frame
(main_window.py:803-805):

So it always reads a FRESH per-frame detection result: its argument `r` is
the `ClothTrackingResult` just returned by `run_cloth_tracking()` this same
frame (never the `_cached_cloth_detections` fallback — that fallback is
display-only, used only inside the `else` branch when Hough is skipped,
which never calls `_apply_cluster_stop_edge`).

Downstream chain from there:
  - `StateMachine.handle_stop_tuchabzug_trigger()` (viscontrol/core/state_machine.py:148-157)
    sets `self._ctx.stop_tuchabzug = True` if `tuchabzug_running` is True.
  - `MainWindow._push_signals_to_opcua()` (main_window.py:2342-2352) reads

  - `MainWindow._request_plc_stop_pulse()` (main_window.py:2387-2394) calls

    `PlcClient.send_stop_pulse()` (viscontrol/io/plc_client.py:186-188) —

Firing is permanent per cluster: once a cluster is `mark_done`, its pieces
are excluded from all future clustering (via `DonePieceTracker`), so a
physical row fires exactly once, never re-fires, and is never re-checked.

5. TRANSFER EVENT TRACKER INTEGRATION
================================================================

`TransferEventTracker.update()` is called exactly once per frame, inside
`_apply_cluster_stop_edge()`, immediately after the real
`cluster_by_tangent()` call from section 4(a) and BEFORE the active-target
fire check (main_window.py:1439-1463):

    # --- DIAGNOSTIC/VISUALIZATION ONLY: TransferEventTracker (see
    # viscontrol/transfer_event_tracker.py). Observes the same
    # current_clusters computed just above, purely for a debug overlay +
    # [TRACKER] logging — it never feeds back into target selection,
    # mark_done, or any StopTuchabzug/PLC path below. Never allowed to
    # crash the frame loop.
    if self.transfer_tracker is not None:
        try:
            _tracker_snapshots = [
                ClusterSnapshot(
                    cluster_id=_ci,
                    front_tangent=cluster.front_tangent_x,
                    back_tangent=max(p.tangent_x for p in cluster.pieces),
                    center_tangent=(
                        cluster.front_tangent_x + max(p.tangent_x for p in cluster.pieces)
                    ) / 2.0,
                    piece_count=len(cluster.pieces),
                    center_y=sum(p.center_y for p in cluster.pieces) / len(cluster.pieces),
                )
                for _ci, cluster in enumerate(current_clusters)
            ]
            self.transfer_tracker.update(_tracker_snapshots, self._frame_count, transfer_x)
        except Exception:  # noqa: BLE001
            logger.exception("[TRACKER-ERROR] transfer_tracker.update failed")
    # --- END DIAGNOSTIC ---

It receives:
  - `_tracker_snapshots`: a list of `ClusterSnapshot` objects
    (viscontrol/transfer_event_tracker.py:24-32) built from the SAME
    `current_clusters` used for real firing (section 4a) — i.e. the
    DONE-piece-filtered, freshly-Hough-derived proximity clusters for this
    frame — but re-packaged into the tracker's own plain shape
    (front_tangent, back_tangent, center_tangent, piece_count, center_y).
  - `self._frame_count`: the running frame counter.
  - `transfer_x`: the transfer line's cloth-local x coordinate.

Connection to the real firing path: NONE. The call is read-only with
respect to `current_clusters` (it only reads them to build snapshots) and
its output (`self.transfer_tracker.events`) is consumed in exactly one
other place — the display/overlay block (main_window.py:1062-1071) — to
build `_transfer_events_overlay` for `set_cloth_frame(..., transfer_events=...)`,
which is purely visual (drawn by `_draw_transfer_events`,
camera_view.py:542). The tracker never calls back into
`ClusterTracker`, `DonePieceTracker`, `StateMachine`, `_request_plc_stop_pulse`,
or any OPC UA/PLC code. Its own module docstring
(transfer_event_tracker.py:12-13) states: "Do not wire this into any
StopTuchabzug, PLC, or fire-decision code path" — and no code in the
repository does so. The entire call (construction and `.update()`) is
wrapped in try/except so a tracker exception can never crash the frame
loop or affect firing (main_window.py:1445-1462, and shutdown at
main_window.py:424-428).

6. FRAME LOOP STRUCTURE
================================================================

In plain text:

- Frame ACQUISITION runs on a dedicated background thread owned by the
  active camera backend (`MockCamera`, `BaslerCamera`, or `PlaybackCamera`
  — viscontrol/io/camera.py, each spawning `threading.Thread(target=_loop,
  ...)` at lines ~167, ~317, ~440). Each iteration of that thread's loop
  grabs/produces one frame and calls the `on_frame` callback, which is
  `_FrameBridge.emit_frame()` (main_window.py:95-99).

- `_FrameBridge.emit_frame()` applies simple backpressure: if the GUI
  thread is still processing the previous frame (`self._processing` is
  True), the new frame is silently dropped and counted
  (main_window.py:96-98); otherwise it emits a Qt signal (`new_frame`)
  that queues the frame for the GUI thread.

- The GUI/Qt thread's event loop (started by `app.exec()` in
  viscontrol/main.py:129) delivers that queued signal to
  `MainWindow._on_frame()` (main_window.py:627), a `@Slot(object)` — this
  is where essentially ALL per-frame processing happens: ROI split,
  tripwire/Hough detection, belt inspection, cluster tracking, firing,
  proximity-cluster and TransferEventTracker diagnostics, and the
  throttled UI redraw. It always runs on the main/GUI thread, one frame at
  a time (guarded by `_processing`).

- RUNS EVERY FRAME (frame rate = camera acquisition rate):
    - `_on_frame()` itself (recorder submit, ROI split, view "current
      frame" caches).
    - The rising/falling `tuchabzug_running` edge check
      (main_window.py:728-729).
    - The belt-inspection window open/close check
      (`_read_belt_inspect_signal`, main_window.py:855-860).
    - Frame-drop/perf-timing bookkeeping.

- RUNS CONDITIONALLY, GATED BY FRAME-COUNT / TIME INTERVALS (still inside
  `_on_frame`, NOT a separate thread or QTimer):
    - Cloth Hough detection (`run_cloth_tracking`) — gated by
      `_hough_due` (main_window.py:740-745): requires
      `hough_interval_ms` (config/default.yaml:126, default 100ms i.e.
      ~10Hz) to have elapsed AND `self._frame_count %
      tripwire_check_interval == 0` (config/default.yaml:43, default 1 =
      every frame is eligible). Also staggered one frame relative to belt
      detection when both are due (main_window.py:744-745) to avoid two
      expensive OpenCV passes on the same frame.
    - `_apply_cluster_stop_edge` / `_track_row_phase` (the fire decision)
      — run only when Hough ran this frame (main_window.py:803-805), so
      firing itself is exactly as frequent as Hough, never faster.
    - Belt inspection (`run_belt_inspection`) — gated by
      `belt_check_interval` (config/default.yaml:44) AND only while the
      belt-inspection window is open or a fault is active
      (main_window.py:864-866).
    - Column-learning diagnostic — runs only alongside a Hough pass
      (main_window.py:773-796), never independently.
    - Proximity-cluster diagnostic overlay + `cluster_by_tangent` call (b)
      and `TransferEventTracker.update()` — both nested inside the display
      throttle (see next bullet) and gated by their own `enabled` config
      flags.

- RUNS ON A SEPARATE THROTTLE (still same thread, same `_on_frame` call —
  not a different thread): the expensive QImage/QPixmap conversion and
  `set_cloth_frame`/`set_belt_frame` UI update is capped to
  `_DISPLAY_INTERVAL_S` = 1/15s (~15fps) regardless of camera or detection
  rate (main_window.py:74-77, 929-1122), so display never becomes the
  bottleneck for detection/firing.

- RUNS ON OTHER, GENUINELY SEPARATE THREADS (not part of the frame loop at
  all):
    - `PlcClient` (viscontrol/io/plc_client.py): its own worker thread
      polls the real PLC over OPC UA at `poll_interval_s`
      (config/default.yaml, plc section) and drains a command queue
      (`send_stop_pulse`/`set_error`/`clear_error`) queued from the GUI
      thread; it calls back into `MainWindow` via
      `on_tuchabzug_change`/`on_error_quit_change` callbacks
      (`attach_plc_client`, main_window.py:392-398), which the callback
      implementation re-enters through normal (GUI-thread-safe, since
      opcua's own thread calls these directly — see plc_client.py for the
      exact threading contract) Qt slots.
    - `WebServer` (viscontrol/io/web_server.py): FastAPI sidecar on its
      own thread, only reads `self._web.set_latest_jpeg(...)` pushed from
      `_on_frame` at a throttled ≤2fps (main_window.py:1125-1138).
    - `FrameRecorder` (viscontrol/io/recorder.py) and
      `ViewVideoRecorder`/video_recorder.py: background writer threads fed
      by non-blocking `submit()` calls from `_on_frame`
      (main_window.py:647-648).

Summary: Hough detection is NOT called every frame — it is rate-limited by
`hough_interval_ms` and `tripwire_check_interval`, and further staggered
against belt inspection. Cached detections from the last Hough run are
reused for display (and only display) on the frames in between. The real
fire decision (`_apply_cluster_stop_edge`) only ever runs on frames where
Hough just ran, so it always sees fresh data.

viscontrol/io/plc_client.py        — Production OPC UA CLIENT to the real PLC: polls signals and queues stop-pulse/error writes on its own worker thread.
viscontrol/io/recorder.py          — FrameRecorder: calibration tooling that writes raw frames to disk on a background thread; no effect on detection/firing.
viscontrol/io/storage.py           — Filesystem helpers: save_defect_image, unexpected-reboot detection/marking.
viscontrol/io/video_recorder.py    — ViewVideoRecorder: background-thread MP4 recorder of the processed inference view (review/observability only).
viscontrol/io/web_server.py        — Read-only FastAPI sidecar (GET-only dashboard, optional basic-auth) running on its own thread.

viscontrol/ui/__init__.py          — Package docstring for the Qt UI layer.
viscontrol/ui/i18n.py              — Installs Qt translators (English/German) for `tr()`-wrapped UI strings.
viscontrol/ui/main_window.py       — MainWindow: the controller — owns camera/detector/pipeline/state machine/event log, the frame loop (_on_frame), and the sole StopTuchabzug fire decision.
viscontrol/ui/theme.py             — Centralized theme constants (colors, fonts, radii) used by all widgets.
viscontrol/ui/views/__init__.py    — Package docstring for top-level views.
viscontrol/ui/views/capture_view.py — CAPTURE view: single-shot camera preview + "Save snapshot".
viscontrol/ui/views/inference_view.py — Main INFERENCE view: belt/cloth CameraView widgets, PLC signal pills, counts, start/stop controls.
viscontrol/ui/views/review_view.py — REVIEW view: browse historical fault images and the event CSV log.
viscontrol/ui/views/service_view.py — SERVICE view: PIN-gated settings (mode, profiles, diagnostics toggles, calibration).
viscontrol/ui/views/wizard_view.py — Installation Wizard: 5-step guided camera/ROI/crop/detection-method setup flow.
viscontrol/ui/widgets/__init__.py  — Package docstring for reusable widgets.
viscontrol/ui/widgets/camera_view.py — CameraView/_Canvas: paints the ROI image plus all detection/tripwire/cluster/transfer-event overlays in paintEvent.
viscontrol/ui/widgets/recent_defects.py — Recent Defects list widget (most-recent first, capped by config).
viscontrol/ui/widgets/sidebar.py   — Left navigation sidebar widget.
viscontrol/ui/widgets/signal_pill.py — Small PLC signal indicator widget (name + colored dot + TRUE/FALSE).
viscontrol/ui/widgets/state_banner.py — Large color-coded state label widget.
viscontrol/ui/widgets/status_bar.py — Bottom status bar (camera/profile/mode/OPC UA/web/disk/timestamp segments).
viscontrol/ui/widgets/stat_card.py — Simple "label + big number" stat card widget.
