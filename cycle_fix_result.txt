CYCLE LIFECYCLE FIX — RESULT
==============================

ROOT CAUSE (see cycle_inspection.txt for the full trace)
----------------------------------------------------------
MainWindow._on_frame() computed its own rising-edge flag purely from
comparing consecutive frames' StateMachine snapshots
(main_window.py:774, before the fix):

    _is_rising_edge = snap.tuchabzug_running and not self._prev_tuchabzug_running
    self._prev_tuchabzug_running = snap.tuchabzug_running
    if snap.tuchabzug_running:
        if _is_rising_edge:
            self._reset_tracking_session()

This fired on EVERY physical tuchabzug_running rising edge — i.e. once per
ROW (a cloth stops/restarts once per row to hand each row to the belt), not
once per CLOTH. _reset_tracking_session() unconditionally called
orchestrator.start_cycle(), which abandons every non-terminal row
(transfer_orchestrator.py, start_cycle(), "row.state = RowState.ABANDONED").
So the very row that was sitting in TRANSFER_PENDING waiting for this exact
rising edge to become TRANSFERRING was abandoned instead — matching the
reported evidence exactly (rows_total=5 transferred=0 abandoned=5).

The orchestrator's actual PLC rising/falling-edge handlers
(_process_plc_cloth_start / _process_plc_stop_ack) were ALREADY correct —
they only ever did the single legitimate row transition each is responsible
for. The bug was entirely in MainWindow's redundant, session-unaware reset
trigger.


WHAT CHANGED
--------------

1. viscontrol/core/transfer_orchestrator.py

   a) start_cycle() now takes a required-in-spirit `reason` parameter
      (default "session_start" for backward compatibility with existing
      positional-only call sites in tests/test_transfer_orchestrator.py)
      and logs it on CYCLE-START:

          def start_cycle(self, source_frame_id: int, reason: str = "session_start") -> None:
              ...
              self._log(
                  "CYCLE-START", level="info", action="start_cycle", result="ok",
                  reason=reason, extra_cycle=self._cycle_id, extra_frame=source_frame_id,
              )

   b) New idle-based new-cloth trigger (STEP 2d), evaluated once per
      OBSERVATION event, at the top of _process_observation():

          now = self._now()
          no_owning_row = not any(r.state in _OWNING_STATES for r in self._rows.values())
          if no_owning_row and (now - self._last_fresh_observation_ts) > self._cycle_idle_reset_s:
              self.start_cycle(event.source_frame_id, reason="idle_timeout")
          if event.observations:
              self._last_fresh_observation_ts = now

      `_last_fresh_observation_ts` is a new instance attribute, initialized
      in __init__ and reset every time start_cycle() runs (either reason).
      The `no_owning_row` guard (reusing the existing _OWNING_STATES tuple:
      STOP_REQUESTED, STOPPED, TRANSFER_PENDING, TRANSFERRING) is mandatory
      and unconditional — an in-flight transfer can never be interrupted by
      an idle timeout (verified by test C4).

   c) New constructor parameter `cycle_idle_reset_ms: int = 3000` wires
      cfg.detection.cycle_idle_reset_ms (previously dead — see
      cycle_inspection.txt part F) into `self._cycle_idle_reset_s`. Default
      of 3000 keeps tests/test_transfer_orchestrator.py's
      `TransferOrchestrator(cfg=cfg, stop_command_sink=sink, now_fn=clock,
      logger=rec_logger)` call (no new kwarg) working unchanged.

   d) _process_plc_cloth_start()'s success log changed from prefix
      "TRANSFER-START"/action="transfer_start" to the STEP 2a-specified
      prefix "CYCLE-CONTINUE"/action="cloth_restart"/
      reason="row_transfer_started". No other line in that method changed —
      it already did exactly one thing (TRANSFER_PENDING -> TRANSFERRING),
      never called start_cycle(), never abandoned a row. This was VERIFIED,
      not modified in behaviour.

   e) _process_plc_stop_ack() (the falling-edge handler,
      STOP_REQUESTED -> STOPPED -> TRANSFER_PENDING) was VERIFIED
      unchanged — already correct, no edits made to it.

2. viscontrol/ui/main_window.py

   a) TransferOrchestrator construction now passes the config value through:

          self._orchestrator = TransferOrchestrator(
              cfg=self._cfg.transfer_orchestrator,
              stop_command_sink=_orchestrator_stop_sink,
              now_fn=time.monotonic,
              logger=logger,
              cycle_idle_reset_ms=self._cfg.detection.cycle_idle_reset_ms,
          )

   b) THE FIX — removed the illegitimate per-row-restart trigger from
      _on_frame(). Removed lines (previously main_window.py:774-779):

          _is_rising_edge = snap.tuchabzug_running and not self._prev_tuchabzug_running
          self._prev_tuchabzug_running = snap.tuchabzug_running
          if snap.tuchabzug_running:
              # Reset per-cycle state on the very first frame of a new cloth pull.
              if _is_rising_edge:
                  self._reset_tracking_session()

      `self._prev_tuchabzug_running = snap.tuchabzug_running` is kept
      (still reset to False in _disable_detection, still initialized in
      __init__) but no longer drives any reset — the `_is_rising_edge`
      computation and the call to _reset_tracking_session() are gone.
      Session/cycle boundaries are now owned exclusively by _on_sm_change
      (real WAITING/READY -> TRACKING transitions) and the orchestrator's
      own idle-timeout.

   c) start_cycle() now has exactly two legitimate call sites in the whole
      codebase (STEP 2c/5 requirement) — the internal idle-timeout call
      inside transfer_orchestrator.py, and the one inside
      _reset_tracking_session(). To satisfy this, the two other call sites
      found in STEP 1 part A were changed to route through
      _reset_tracking_session() instead of calling
      orchestrator.start_cycle() directly (both are genuine explicit
      operator/session-start events, not per-row restarts):

      - _disable_detection() (STOP button). Removed:

            try:
                self._orchestrator.start_cycle(self._frame_count)
            except Exception:  # noqa: BLE001
                logger.exception("[ORCH-ERROR] orchestrator.start_cycle failed (STOP button)")
            if self._layout_monitor is not None:
                self._layout_monitor.reset()

        Replaced with a single call to self._reset_tracking_session() (which
        itself calls start_cycle(reason="session_start") and
        layout_monitor.reset(), among the same tracker resets
        _disable_detection already performs inline).

      - The wizard-completion handler. Removed:

            try:
                self._orchestrator.start_cycle(self._frame_count)
            except Exception:  # noqa: BLE001
                logger.exception("[ORCH-ERROR] orchestrator.start_cycle failed (wizard completed)")
            if self._layout_monitor is not None:
                self._layout_monitor.reset()

        Replaced with self._reset_tracking_session().

      - _reset_tracking_session() itself now calls start_cycle with an
        explicit reason:

            self._orchestrator.start_cycle(self._frame_count, reason="session_start")

3. viscontrol/core/layout_quality.py — LayoutQualityMonitor.reset()'s
   docstring updated (comment only, no behaviour change) since it
   previously said "call ... on new TuchabzugRunning pull" as a legitimate
   start_cycle() site, which was the bug being fixed.

Nothing in RowAssociator, cluster_by_tangent, the fire/stop decision,
_request_stop, stop idempotency, PlcClient threading, or OPC UA node
handling was touched. No new config keys were added —
cfg.detection.cycle_idle_reset_ms (already present, previously dead) is now
wired into the orchestrator.
