   THE BUG, see part D).

No call sites exist inside viscontrol/core/transfer_orchestrator.py itself
(other than the start_cycle() method definition at line 168) or anywhere
else in viscontrol/.

D. EXACTLY WHICH LINE CAUSES ROWS TO BECOME ABANDONED ON A CLOTH RESTART
----------------------------------------------------------------------------

  transfer_orchestrator.py:168-191, start_cycle():

       168	    def start_cycle(self, source_frame_id: int) -> None:
       ...
       176             ts = self._now()
       177             for row in self._existing_rows_sorted():
       178                 if row.state not in _TERMINAL_STATES:
       179                     old_state = row.state
       180                     row.state = RowState.ABANDONED
       181                     row.history.append((ts, old_state, RowState.ABANDONED, "cycle_restart"))

  Line 180 is the actual abandon. It is reached because _on_frame's rising-
  edge poll (main_window.py:778-779, Path 2 above) calls
  _reset_tracking_session(), which unconditionally calls
  orchestrator.start_cycle() (main_window.py:2630) on EVERY physical rising
  edge — i.e. once per ROW within a cloth, not once per CLOTH. Every row
  that was sitting in TRANSFER_PENDING (waiting for exactly this rising
  edge to become TRANSFERRING) gets swept into ABANDONED by start_cycle()
  before _process_plc_cloth_start ever gets a chance to run — this matches
  the observed evidence exactly (rows_total=5 abandoned=5 transferred=0).


E. IS _reset_tracking_session INVOKED ON A PLC EDGE?
-------------------------------------------------------

  Yes, indirectly — but not directly from any PLC callback. It's invoked
  from two places:

  1) main_window.py:2604, inside _on_sm_change():

         2600	    def _on_sm_change(self, old: State, new: State) -> None:
         2601	        if new == State.TRACKING:
         2602	            QTimer.singleShot(0, self._reset_tracking_session)

     _on_sm_change is registered as an SM on_change listener
     (presumably in __init__ via self._sm.on_change(self._on_sm_change), and
     only fires when StateMachine._transition() actually changes state
     (state_machine.py:100-115) — i.e. only on WAITING/READY -> TRACKING,
     which is the genuine first rising edge of a session. A PLC callback
     (_on_plc_tuchabzug_change) triggers this indirectly by calling
     self._sm.handle_tuchabzug_rising(), but only produces an actual
     TRACKING transition (and therefore only fires _on_sm_change) once per
     session — this call site is legitimate and not the source of the bug.

  2) main_window.py:779, inside _on_frame() (Path 2 above) — fires on EVERY
     physical rising edge regardless of SM state change. This is a
     DIFFERENT, redundant trigger with no session-boundary awareness. THIS
     is the illegitimate site causing the bug.

  This fix wires it into TransferOrchestrator for the first time (STEP 2d).
