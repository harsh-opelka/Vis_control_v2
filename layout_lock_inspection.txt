B. Piece / ClusteredPiece field names
------------------------------------------------
File: viscontrol/detection/proximity_clustering.py

    class Piece(NamedTuple):

        center_x: float
        center_y: float

    @dataclass

        center_y: float

`tangent_x` field name: `tangent_x` (on ClusteredPiece — the objects
actually stored in `ProximityCluster.pieces`).
`center_y` field name: `center_y` (on both Piece and ClusteredPiece).

ProximityCluster (also proximity_clustering.py):

    @dataclass
    class ProximityCluster:
        pieces: list[ClusteredPiece]

        @property
        def front_tangent_x(self) -> float:
            return min(p.tangent_x for p in self.pieces)

So the real path to a piece's tangent_x from a `clusters: list[ProximityCluster]`
is `cluster.pieces[i].tangent_x`. Per the task instructions, center_y must
NEVER be used by this feature — only tangent_x.

G. Does anything already block stops while a fault is active?
------------------------------------------------
No — confirmed by two independent pieces of evidence:

1. state_machine.py:148-157, handle_stop_tuchabzug_trigger():

    def handle_stop_tuchabzug_trigger(self) -> bool:
        """A row crossed the transfer line; assert StopTuchabzug.

        Fires whenever TuchabzugRunning is True, regardless of internal state,
        so the tripwire works during FAULT as well as TRACKING.
        """
        with self._lock:
            if self._ctx.tuchabzug_running:
                self._ctx.stop_tuchabzug = True
            return False

   This explicitly fires during FAULT by design (belt faults must not
   silently stop the cloth from also tracking/stopping rows).

2. main_window.py:_on_frame — `_run_transfer_orchestrator(r, profile)`
   (line 819) is called unconditionally inside the
   `if snap.tuchabzug_running:` block whenever Hough is due, with no
   `snap.fault_active` check anywhere in that branch. Only the BELT
   inspection branch (line 878, `_needs_belt = self._belt_inspect_window_open
   or snap.fault_active`) reads fault_active — that gates belt
   detection cadence, not cloth/row stop firing.

Conclusion: nothing today stops the orchestrator from continuing to
fire StopTuchabzug commands while a fault (belt or otherwise) is
active. This means STEP 2d's "block new stop commands from the
orchestrator while locked" is a genuinely NEW guard, not something
that needs to cooperate with an existing block — it must be added
inside `_orchestrator_stop_sink` (or equivalent) as its own check
against `self._layout_monitor.is_locked`, without touching
`handle_stop_tuchabzug_trigger` or the orchestrator's own idempotency
guard (`row.stop_event_id is not None`, transfer_orchestrator.py:458).
