3. DELAYED CALLS (0-100ms) THAT TOUCH WINDOW GEOMETRY AFTER __init__
------------------------------------------------------------------------------
No delayed call in viscontrol/ui/main_window.py directly calls resize/
setGeometry/adjustSize/move. There are two QTimer.singleShot(0, ...) calls
— true 0ms delay, i.e. "next event-loop tick" — but neither touches

  viscontrol/ui/main_window.py:2587-2588 (inside _on_sm_change, fired every
  time the StateMachine's on_change listener runs — registered at
  main_window.py:391):

        if new == State.TRACKING:
            QTimer.singleShot(0, self._reset_tracking_session)
        QTimer.singleShot(0, lambda: self._refresh_state(new))

  _refresh_state (viscontrol/ui/main_window.py:2626) only calls

  `self._inference_view.set_machine_status_label(label, color)` →
  StateBanner.set_display() (viscontrol/ui/widgets/state_banner.py:30-36),
  which does `self.setStyleSheet(...)` + `self.setText(label)` on a QLabel

  viscontrol/ui/views/inference_view.py:246-247: `StateBanner(compact=True)`
  / `self.setFixedHeight(40)` inside state_banner.py:24). A stylesheet/text
  change on a fixed-height QLabel does not itself grow the top-level
  window; this is a layout-touching event but not a geometry-setting one.

  These singleShot(0,...) calls only fire when the StateMachine actually
  changes state (on_change listeners are only invoked from `_transition`,
  state_machine.py:100-115, when old != new). Whether one fires "shortly
  after opening" therefore depends on whether anything transitions the SM
  away from its constructed default (State.WAITING) during/after startup —
  no code in main.py calls any force_reset_to_*/handle_* method between

  is only called from viscontrol/ui/main_window.py:618, the STOP button
  handler, and :2410, the wizard-completion handler — neither runs at
  startup).

The one geometry-ADJACENT delayed call that DOES exist is NOT in the
0-100ms range by default, but is a genuine "set height, shortly after
open" event — see item 4.


4. SHOWN ONCE THEN RESIZED AGAIN ELSEWHERE?
------------------------------------------------------------------------------
The window itself is shown exactly once (main.py:111, `window.show()` — no
other show()/showMaximized()/showNormal() call on the MainWindow exists
anywhere). However, the MAIN WINDOW'S CONTENT changes height shortly after
open via a widget inserted into (and later collapsed within) the already-
installed central layout — this is the closest match to "resized again in
a slot connected to a signal that fires shortly after startup":

  a) Insertion (during __init__, before show() — viscontrol/ui/main_window.py:2684-2710):

        def _build_startup_banner(self) -> QFrame:
            banner = QFrame()
            banner.setObjectName("startupBanner")
            banner.setFixedHeight(36)
            ...
            # Insert at the very top of the right-side content column (above the stack).
            self._content_layout.insertWidget(0, banner)
            ...
            QTimer.singleShot(self._cfg.ui.startup_banner_seconds * 1000, _dismiss)
            return banner

     Called from viscontrol/ui/main_window.py:394:
        self._banner = self._build_startup_banner()

     This inserts a 36px-tall QFrame at index 0 of `self._content_layout`
     (viscontrol/ui/main_window.py:368) — a layout that was already handed
     to `setCentralWidget()` four lines earlier at :374's preceding block
     (:359-374). I.e. a widget is added to the central layout's structure
     AFTER the layout was installed, though this still all happens before
     window.show() is ever called (both are inside __init__, which
     completes at main.py:69 before show() at main.py:111).

  b) Auto-dismiss (config-driven delay, default 30000ms — NOT 0-100ms, but
     still a delayed geometry-relevant call with no user interaction):

        def _dismiss() -> None:
            banner.hide()
            banner.setFixedHeight(0)

        close.mousePressEvent = lambda _e: _dismiss()
        QTimer.singleShot(self._cfg.ui.startup_banner_seconds * 1000, _dismiss)

     `cfg.ui.startup_banner_seconds` defaults to 30 (config/default.yaml,
     viscontrol/core/config.py:519 `startup_banner_seconds: int = Field(30, ge=0)`),
     so by default this fires 30s after the banner is built — well outside
     "shortly after opening" for a typical operator, but it IS a real,
     unconditional, timer-driven height change with zero user interaction,
     and it is configurable down to 0 (config/default.yaml sets
     `startup_banner_seconds: 30`; if set to 0, main.py:115-116 calls
     `window.hide_startup_banner()` SYNCHRONOUSLY right after show(),
     collapsing the banner within the same event-loop tick that made the
     window visible):

        # main.py:115-116
        if cfg.ui.startup_banner_seconds <= 0:
            window.hide_startup_banner()

     `hide_startup_banner()` (main_window.py:425-427):
        def hide_startup_banner(self) -> None:
            self._banner.hide()
            self._banner.setFixedHeight(0)

     Since `self._content_layout.addWidget(self._stack, 1)` (main_window.py:371)
     gives the QStackedWidget stretch factor 1 while the banner is a fixed-
     height QFrame, collapsing the banner from 36px to 0px should let the
     stack reclaim that space WITHIN the current window height (shrink the
     banner, not grow the window) — this is a plausible mechanism for a
     visible relayout shortly after open, but its direction (collapsing a
     widget to 0 height) means it is a more likely explanation for a
     visible "content jump" than for the window itself growing.

No other slot connected to any "first frame received"/"layout ready"-style

5. DPI / SCALING SETTINGS
------------------------------------------------------------------------------
No High-DPI attribute is set anywhere in the repo — grep for
"AA_EnableHighDpiScaling", "HighDpiScaleFactorRoundingPolicy",
"setAttribute(Qt" across viscontrol/ returns 0 matches. viscontrol/main.py's
QApplication construction (lines 56-66) does nothing beyond
`app.setApplicationName(...)` / `app.setOrganizationName(...)`:

    app = QApplication.instance() or QApplication(sys.argv)
    app.setApplicationName("VisControl")
    app.setOrganizationName("OPELKA")

Since this project is on PySide6/Qt6 (confirmed by PySide6 imports
throughout), High-DPI scaling is ON by default and not configurable via the
old Qt5-era `AA_EnableHighDpiScaling` attribute (a no-op in Qt6) — so
whatever the platform's DPI scale factor is, it applies automatically and
implicitly with no explicit policy chosen in this codebase.

`self.resize(1400, 900)` (main_window.py:122) and every other geometry call
found (there are none besides this one) use plain integer literals, which
Qt treats as device-independent ("logical") pixels — there is no place in
the codebase that reads `devicePixelRatio()`, `screen().geometry()`, or
otherwise computes a size from physical pixels. This means: on a display
where the OS/monitor DPI scale factor is not exactly 100%, the window's
on-screen (physical) pixel size will differ from 1400x900, but this is a
static scaling difference applied once at show() time by Qt/the platform —
not a mechanism that would produce a VISIBLE post-open growth animation/
jump, since the scale factor doesn't change after launch. No code path
recomputes or re-applies geometry in response to a DPI/screen-change event
(no `screenChanged` handler, no `devicePixelRatioChanged` handler found).


6. STYLESHEET / LAYOUT RECALCULATION ON A TIMER OR FIRST PAINT
------------------------------------------------------------------------------
  - Global stylesheet: applied exactly once, synchronously, in __init__,
    BEFORE any child widget exists (main_window.py:123):
        self.setStyleSheet(GLOBAL_STYLESHEET)
    Not timer-based, not reapplied anywhere else in the codebase (grep for
    "setStyleSheet(GLOBAL_STYLESHEET" — 1 match).

  - Per-widget stylesheet changes that DO happen shortly after open, driven
    by the zero-delay singleShot chain described in item 3
    (_on_sm_change → _refresh_state → _update_banner_from_signals →
    set_machine_status_label → StateBanner.set_display,
    state_banner.py:30-36):

        def set_display(self, label: str, color: str) -> None:
            font_size = FONT_LARGE if self._compact else FONT_HUGE
            self.setStyleSheet(
                f"color: {color}; font-size: {font_size}pt; font-weight: 800; letter-spacing: 4px;"
            )
            self.setText(label)

    This only fires on an actual SM state transition (see item 3) — it is
    NOT unconditionally scheduled on a timer at startup; it is an
    on_change listener side effect. `_refresh_state` is also called once,
    synchronously and unconditionally, from __init__ at main_window.py:390
    with `State.WAITING` — that call happens before the window is even
    shown, so it cannot be the source of a POST-open visible change on its
    own.

  - No `paintEvent` override anywhere in the codebase calls
    `updateGeometry()`, `resize()`, `adjustSize()`, or `setStyleSheet()`
    (checked camera_view.py's `_Canvas.paintEvent` and CameraView's own
    paint handling — they only draw, via QPainter, onto the existing
    widget rect; they never resize the widget or its ancestors).

  - The only OTHER timer-driven, layout-visible change found anywhere in
    MainWindow is the startup-banner auto-dismiss covered fully in item 4
    (`QTimer.singleShot(cfg.ui.startup_banner_seconds * 1000, _dismiss)`,
    main_window.py:2709) — a real relayout trigger, but on a 30s default
    delay, not first-paint-driven.


SUMMARY OF FINDINGS (still just reporting; nothing changed)
------------------------------------------------------------------------------
- There is exactly one explicit size-setting call on the main window in the
  entire codebase: `self.resize(1400, 900)` at main_window.py:122 — and it
  runs BEFORE the central widget, its layout, the startup banner, and any
  child widget (sidebar, camera views, PLC panel, stat cards, etc.) exist.
  Everything that determines the window's actual minimum/preferred size
  (the QVBoxLayout/QHBoxLayout/QGridLayout tree built across
  main_window.py:344-398 and inference_view.py's `_build_*` methods) is
  constructed AFTER this resize() call, then only actually laid out and
  reconciled against real geometry constraints by Qt at the first
  `window.show()` (main.py:111) — which is also the very next thing to
  happen "shortly after opening, before user interaction" from the user's
  point of view. A top-level widget resized before its layout/children
  exist, then shown once its full (deeper-than-anticipated) content tree is
  in place, is a well-known way for Qt to grow a window past its
  explicitly-requested size on first show, to satisfy the now-known
  minimum-size chain (banner + top bar/stat cards + record bar + state
  banner + two Expanding camera views each with a 320x240 floor + PLC
  panel + status bar, stacked in main_window.py's QVBoxLayout hierarchy).
  This is the most concrete, code-grounded candidate mechanism found for a
  content-driven, pre-interaction resize, though confirming it visually
  (does the window's actual on-screen size differ from 1400x900 the moment
  after show() returns) was not done here, per the report-only scope of
  this task.
- The startup banner's insertion into an already-installed layout (item 4a)
  and its later collapse (item 4b, default 30s, or immediately if
  `startup_banner_seconds` is configured to 0) are the only other
  concrete, code-grounded, pre-interaction geometry-relevant events found.
- No QSettings/persisted geometry, no DPI-driven resize logic, no second
  explicit resize()/setGeometry() call, and no paintEvent-triggered
  relayout exist anywhere in the codebase.
