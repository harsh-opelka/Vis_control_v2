ANSWER TO STEP 0 PART A'S AMBIGUITY
-------------------------------------------------------------------
Question: for a row that geometrically crosses the tripwire but is
blocked from actually stopping (another row already owns the transfer),
or that never crosses at all (abandoned first), do we still want a
"tripwire" photo, or only for rows that actually get stopped?

Resolution: settled by the task's own downstream instructions rather
than guessed — STEP 1 point 4 ("If a row never reaches 'tripwire' ...
still call on_row_cleared ... so every row gets at least 2 of the 3
photos") and test T5's name/description both presuppose that "tripwire"
= "a stop command was actually issued," not "the row's front_tangent
geometrically crossed transfer_x." Implemented exactly that: the
on_row_tripwire callback fires from inside
TransferOrchestrator._request_stop(), immediately after
self._stop_command_sink(row.snapshot) — i.e. only when a real stop
command was issued. A row blocked by the ownership guard, or one
abandoned before ever crossing, simply never gets an on_row_tripwire()
call; it still gets on_row_confirmed() (if it reached ACTIVE) and
on_row_cleared() (at termination) — 2 of 3, never silently 0. Full
reasoning and code quotes are in row_capture_inspection.txt part A.
No user clarification was requested since the prompt already settled it.

Separately flagged (not asked about, documented for the record): a row
abandoned before ever reaching ACTIVE (never "confirmed") gets only 1
of 3 photos ("cleared" only) — this is inherent, not a bug, since it
never passed through "confirmed" either; STEP 1/T5's "2 of 3" guarantee
is specifically about rows that WERE confirmed but never crossed.
