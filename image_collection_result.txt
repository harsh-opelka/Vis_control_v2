BACKGROUND-THREAD CLEANUP (STEP 3)
-------------------------------------------------------------------
Yes, implemented, and necessary per the task's "must not block the GUI
thread for a long time" requirement. `TrainingDataCollector.run_maintenance()`
itself is plain, Qt-free, synchronous code (as required — the module may
not import PySide6). The QTimer lives in MainWindow and fires
`_on_traindata_maintenance_tick`, which:
  1. Returns immediately (no-op) if the collector is disabled.
  2. Returns immediately if a previous maintenance run is still in flight
     (tracked via `threading.Event`), so overlapping cleanup threads can
     never stack up under a slow disk / huge tree.
  3. Otherwise spawns a short-lived daemon `threading.Thread` (named
     "TrainDataMaintenance", matching the existing `FrameRecorder` writer-
     thread pattern in viscontrol/io/recorder.py) that calls
     `run_maintenance()` and clears the guard event in a `finally`.
This mirrors the codebase's existing convention (plain `threading.Thread`,
not `QThread`) already used by `FrameRecorder` for background disk I/O, so
no new threading primitive/pattern was introduced.

MEASURED COMPRESSION RATIO (T7)
-------------------------------------------------------------------
T7 saves a 1000x1000 synthetic uint8 array via `cv2.imencode('.jpg', ...,
[IMWRITE_JPEG_QUALITY, 88])` and asserts the written file is smaller than
the raw uncompressed array and is a valid, readable JPEG. Measured on
pure random noise (the worst realistic case — maximizes entropy, so this
is a deliberately pessimistic bound for the test assertion):
  uncompressed: 1,000,000 bytes   jpeg: 733,742 bytes   ratio: 1.36x

For a more representative estimate, the same encode was run on the
repo's actual mock camera test frames (assets/test_images/*.png, real
Basler-resolution 3200x2200 Mono8 stills, cloth-ROI-cropped to 1432x2200
the same way `split_rois` crops a live frame):
  01_clean.png       cloth ROI 2200x1432 -> jpeg ~52.5 KB (ratio ~58x)
  10_row_fused.png   cloth ROI 2200x1432 -> jpeg ~52.7 KB (ratio ~60x)
  20_column_fused.png cloth ROI 2200x1432 -> jpeg ~53.9 KB (ratio ~57x)
These mock frames are clean/synthetic test fixtures, though, not live
camera captures with real cloth-mesh texture and sensor noise — real
frames will compress less well than this. The storage projection below
therefore uses a bracketed (optimistic / conservative) per-image size
rather than trusting the mock-image number alone.

PROJECTED STORAGE ESTIMATE (normal_sample only, before any
ambiguous/layout_fault images are added)
-------------------------------------------------------------------
Inputs: normal_sample_every_n_rows=20, 350 rows/hour, max_total_size_gb=50,
cloth-ROI JPEG size bracketed at 53 KB (measured, mock frames — optimistic)
to 250 KB (assumed, real textured Basler frames at 1432x2200, q88 —
conservative planning number).

  saves/hour = 350 rows/hour / 20 = 17.5 normal_sample images/hour

  Per-day figures, two operating-hour assumptions:

  8 h/day (single shift):
    images/day = 17.5 * 8 = 140
    optimistic  (53 KB):  140 * 53 KB  =  7,420 KB/day  = 0.00707 GB/day
    conservative(250 KB): 140 * 250 KB = 35,000 KB/day  = 0.0334 GB/day

  24 h/day (continuous line):
    images/day = 17.5 * 24 = 420
    optimistic  (53 KB):  420 * 53 KB  =  22,260 KB/day = 0.0212 GB/day
    conservative(250 KB): 420 * 250 KB = 105,000 KB/day = 0.100 GB/day

  Days until max_total_size_gb=50 is reached (normal_sample alone,
  BEFORE any ambiguous/layout_fault images):
    days = 50 GB / GB_per_day

    8h/day, optimistic:   50 / 0.00707  ≈ 7,071 days  (≈ 19.4 years)
    8h/day, conservative: 50 / 0.0334   ≈ 1,497 days  (≈  4.1 years)
    24h/day, optimistic:  50 / 0.0212   ≈ 2,358 days  (≈  6.5 years)
    24h/day, conservative:50 / 0.100    ≈   500 days  (≈  1.37 years)

Conclusion: at this sampling rate (every 20th row event, ~17.5/hour),
normal_sample alone is nowhere near capable of filling the 50 GB cap
within any realistic product lifetime — even the conservative 24h/day
bound gives >1 year of headroom before the rolling cleanup would ever
need to remove a normal_sample folder. In practice ambiguous/layout_fault
images (always-saved, rarer, same compression) will consume additional
but still small headroom, since layout-lock and ambiguous-match events
are, per the task's own framing, rare hard cases rather than a
steady-state stream. The 50 GB cap and 10 GB min-free-space guard leave
ample margin under the Jetson's ~70 GB currently free / 128 GB total SD
card, even under the conservative bracket.
