THE ROW-COUNTER / DEDUP LOGIC — DOES REMOVING "cleared" BREAK IT?
-------------------------------------------------------------------
Quoted from training_data_collector.py as it stands now (BEFORE this
task's changes):

    def _should_capture_row(self, row_id: int) -> bool:
        """Save-every-Nth-row filter — applies only to row-lifecycle
        capture (never ambiguous/layout_fault/fault). Computed once per
        row_id, on whichever of on_row_tripwire/on_row_cleared arrives
        first; the second call for the same row_id reuses the cached
        decision, so both stages of one row always agree (never one
        saving while the other skips). Bounded FIFO eviction, same
        convention as _mark_if_new above.
        """
        cached = self._row_sample_decisions.get(row_id)
        if cached is not None:
            return cached

        self._rows_seen_count += 1
        every_n = max(1, self._cfg.capture_every_n_rows)
        decision = self._rows_seen_count % every_n == 0

        self._row_sample_decisions[row_id] = decision
        self._row_sample_eviction_order.append(row_id)
        bound = max(1, self._cfg.max_tracked_row_ids)
        while len(self._row_sample_eviction_order) > bound:
            oldest = self._row_sample_eviction_order.popleft()
            self._row_sample_decisions.pop(oldest, None)
        return decision

`self._row_sample_decisions` (+ its eviction deque) exists FOR EXACTLY
ONE REASON: to let two independent call paths (tripwire and cleared) for
the SAME row_id agree on one save/skip decision without incrementing
`_rows_seen_count` twice. Once `on_row_cleared` is removed, `on_row_tripwire`
is the ONLY entry point into `_capture()` — and `_capture()` already gates
every call through `_mark_if_new(row_id, stage)` FIRST
(training_data_collector.py:232-237), which returns `False` (and returns
early, BEFORE `_should_capture_row` is ever reached) on any genuine
duplicate call for the same `(row_id, "tripwire")` pair. So with only one
stage left, `_should_capture_row` can never legitimately be invoked twice
for the same row_id — the per-row-id cache becomes provably dead weight,
not just unused-but-harmless: every code path that could have exercised
the "second call reuses the cached decision" branch is gone once
`on_row_cleared` no longer exists. Removing it is safe AND required by
this task's own "do not leave dead both-stages-agree logic" constraint.

REPLACEMENT DESIGN (implemented in STEP 1): `_should_capture_row` no
longer needs a row_id-keyed cache at all — it becomes a straight,
unconditional increment-and-modulo check, called once per genuine (i.e.
past `_mark_if_new`) tripwire capture. `self._row_sample_decisions` and
`self._row_sample_eviction_order` are deleted entirely, not just
unwired — there is no future call path that could ever populate or read
them once `on_row_cleared` is gone.

CONCLUSION: removing `on_row_cleared` is a clean, fully isolated deletion.
Nothing else in the codebase depends on it running, and the row-counter's
per-row-id cache can be simplified (not just left dangling) once it is
gone.
